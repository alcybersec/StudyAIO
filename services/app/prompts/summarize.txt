## Output Requirements

Generate a complete markdown summary with EXACTLY these sections in this order:

1. `# {{ course_code }} — Week {{ week }}: <Topic>` (determine the topic from the content)

2. `## Overview` — 1-2 paragraphs that contextualize the topic: what it is, why it matters, and how it fits into the broader subject. Set the stage before diving into details.

3. `## Key Concepts` — This is the core of the summary and should be the longest section. Organize concepts into hierarchical subsections using `###` and `####` headers that reflect the logical structure of the material. For each concept:
   - Explain the "what", "why", and "how" — not just definitions
   - Write in paragraph form with supporting details
   - Weave in real-world examples, case studies, and scenarios from the lecture
   - Use tables where comparison or structured data is natural (e.g. tool comparisons, attack type vs. defense)
   - Use bullet lists only for genuinely list-like content (tool names, enumerated steps, short items)
   - Build concepts progressively — introduce foundations before advanced topics
   Do NOT produce a flat bullet-point dump. Think like a tutor explaining the material to a student.

4. `## Definitions` — Markdown table with columns: Term | Definition. Include all key terms. This supplements the Key Concepts section — terms should already be explained in context above.

5. `## Diagrams & Visual Descriptions` — For important processes, architectures, or relationships from the lecture, create ASCII art diagrams with explanatory text (e.g. network topologies, attack flows, process pipelines, memory layouts). Also reference extracted images ONLY if they aid understanding (architecture diagrams, flowcharts, process diagrams, data models). SKIP simple shapes, clip art, stock photos, decorative images, and screenshots of text/tables. If no valuable visual content exists, write "No diagrams in this lecture."

6. `## Code Examples` — Include code examples from the lecture with inline comments explaining each significant line or block. Add a brief note about when and why each example is relevant. If none, write "No code examples in this lecture."

7. `## Formulas & Algorithms` — Include any mathematical formulas, calculations, algorithms, or quantitative relationships from the lecture. Use code blocks or LaTeX notation ($...$). If none, write "No formulas in this lecture."

8. `## Key Takeaways` — Bullet list of the most important lessons and insights from the lecture. Write as distilled "so what?" statements that capture why each point matters — not just restating facts.

9. `## Connections` — 2-4 paragraphs linking this week's material to other lectures in this course. Ground every connection in something this lecture actually said: a concept it named, a problem it left open, a technique it built on. Where the lecture itself points beyond its own scope ("we will cover X next week", "this is used in Y"), follow that pointer and attribute it. Do NOT introduce named technologies, algorithms, standards or industry practices the lecture did not mention: a student revising from this cannot tell your additions from the lecturer's, and the exam will test the lecturer's.

10. Footer line: `---` followed by `*Sources: <list source artifacts>. Version: 1.*`

## Rules
- Write as a tutor teaching the material, not a transcription service listing facts
- Explain concepts in depth with context and examples — avoid shallow bullet-point dumps
- Organize Key Concepts hierarchically (### and ####) to reflect the logical structure of the lecture
- Be thorough on important concepts, brief on minor ones — match depth to significance
- Use proper markdown formatting
- Include ALL key definitions and concepts from the lecture
- Preserve technical accuracy — do not invent information not present in the lecture content
- Prefer paragraph-form explanations over flat bullet lists for conceptual material
